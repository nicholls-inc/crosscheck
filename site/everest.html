A one-second difference
you can inspect.

A daily charging schedule should restart at 11:00:00. In the study’s smallest example, EVerest restarts it at 10:59:59. The physical impact is small; the difference is concrete and repeatable.

This is a worked example of the argument in Review Evidence, Not Code (opens in a new tab). Follow the claim from a written rule to its supporting checks, human decisions and limits.

Follow one claim

Written rule → reference program → test witness → repeatable run.

The study rates this as low severity. Daily and weekly restarts drift by one second per since the original schedule start.

The signed interpretation is that a daily schedule restarts at the clock time in its startSchedule. The study records that the standard’s wording also admits another reading. This interpretation is a stated premise of the finding.

The input has one daily default profile, no duration, and two periods: 9,249.9 W from offset 0, then 6,543.6 W from offset 40,500 seconds. Its query window begins at 03:00:00 UTC on 13 August 2026 and lasts 24 hours.

EVerest calculates recurrence using elapsed UTC seconds, which include leap seconds. The reference program follows the signed clock-time interpretation. The study’s diagnostic rerun shifts older anchors forward by the intervening leap seconds; all 2,000 cases then pass. That changes the inputs to isolate the cause. It is not a fix to EVerest.

The driver compiles unmodified EVerest scheduling code, but supplies its own installation and orchestration glue and two shim headers. Those dependencies are part of what the comparison trusts.

What is proved

checks mathematical arguments about the model. This is not a proof of the C++ implementation.

  • The combined limit is never above the charger-wide limit.
  • It is never above the applicable transaction limit.
  • While a transaction's own schedule applies, changing default schedules does not change the limit.

Unfinished: Adding a lower-priority schedule that does not apply leaves the limit unchanged (I4).

The proof check names the completed theorems and rejects dependencies on sorryAx or non-standard axioms. A fourth, unfinished statement must not be counted as proved.

Where people decided

An AI correspondence review searched for likely problems. The recorded owner decisions supply the human judgment; the model’s verdict is not evidence.

  • The owner approved interpretations A1 and A2 and reclassified two AI correspondence-review findings as abstractions rather than approximations.
  • The owner confirmed restoring the missing s ≤ t condition in D4 on 2026-10-27.
  • Q4 treats lower limits as conforming; the owner chose to warn about lost charging. The report retains the classification caveat recorded here.

What this depends on

The is part of the claim, not a footnote to it.

  • Lean v4.28.0 and its standard axioms propext, Classical.choice and Quot.sound for the stated completed proofs.
  • The reviewed interpretation of OCPP 1.6 edition 2 and the Lean model's correspondence to it.
  • The C++ compiler, driver, copied installation/orchestration glue, two shim headers, Python harness, JSON adapter and model runner.
  • The operating system timezone database read by the driver; its leap-second table must contain exactly the three leap seconds since 2010 (2012-06-30, 2015-06-30, 2016-12-31).

Where the result stops

Matching these inputs does not establish all OCPP behavior. Each unreached behavior needs a model extension or an explicit assumption.

At most 2 charger-wide, 3 default and 2 transaction profiles, up to 4 periods per profile, 15-minute offsets, 24- or 48-hour windows in 2026, on connector 1. Absolute, daily and weekly schedules are generated. Each case samples transition instants from either program and one second either side.

Default profiles on connectors 0 and 1 together are not generated: the signed spec leaves their interaction unresolved. The recurrence wording also admits another interpretation; the study records it as OCA note N4.

Repeat the run

Start from the pinned study revision, not the moving pull-request branch. Setup downloads dependencies; this is not the plugin’s Docker workflow.

Install elan with leanprover/lean4:v4.28.0, Python 3, git and curl. The recorded driver build used Apple clang 21.0.0, C++17; reported on macOS arm64, Boost 1.92.0, headers under /opt/homebrew/include and fmt 12.2.0, header-only under /opt/homebrew/include. See the driver prerequisites (opens in a new tab) before running.

Source and downloaded inputs are pinned. The host compiler, system headers and timezone database still need matching; this is not a hermetically pinned environment. The leap-second table must list the three leap seconds since 2010. The driver build checks downloaded sources against SHA-256 hashes in the pinned build script (opens in a new tab).

git clone https://github.com/nicholls-inc/crosscheck crosscheck-everest-study
cd crosscheck-everest-study
git checkout --detach 7d05c4e62284b4101e8f23722ee3b6111e5ca0e9
formal-verification/tests/ocpp16_composite/everest_driver/build.sh
formal-verification/lean/CrosscheckModel/check_ocpp16_composite.sh
python3 formal-verification/tests/ocpp16_composite/drt_harness.py --count 2000 --seed 20261024
python3 formal-verification/tests/ocpp16_composite/drt_harness.py --count 2000 --seed 20261024 --old-anchors
python3 formal-verification/tests/ocpp16_composite/drt_harness.py --count 2000 --seed 20261024 --old-anchors --leap-correct

The older-anchor run is expected to report failures; a nonzero exit is a reproduced finding, not an installation failure. --leap-correct changes input anchors for diagnosis and does not fix EVerest. A run writes drt_report_latest.md; preserve the pinned historical report.
