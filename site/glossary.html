EVerest and OCPP 1.6: a formal study

Glossary

The specialist terms used on this site, in plain English. On the study page, each dotted term opens the same explanation.

Proof
A computer-checked mathematical argument that a rule always holds under stated assumptions. It does not tell us whether the rule is the right one.
Lean
A language for precisely describing how code should behave, and a tool for checking mathematical arguments about those descriptions.
Reference program
A program describing the behavior we expect. We compare its answers with the code being checked. It covers only the behavior it describes.
Leap second
An extra second sometimes added to clock time to keep it in line with Earth’s rotation.
Differential testing
Run the same chosen inputs through two programs and compare their answers. A difference needs investigation. Matching answers cover only the inputs tried.
EVerest
Open-source software for running an electric-vehicle charging station, maintained as a Linux Foundation Energy project. This study tested its code for combining charging schedules.
Its own documentation calls it “a full-stack environment for EV-charging”. It was started by Pionix GmbH and is released under the Apache 2.0 licence. Among its modules is support for OCPP 1.6 and 2.x. The study tested EVerest’s unmodified C++ code that works out a charger’s power limit from its charging schedules, at source revision dd696165. EVerest documentation (opens in a new tab)
OCPP
Open Charge Point Protocol: shared rules for communication between electric-vehicle charging stations and the software managing them. This study checks charging schedules under version 1.6.
The Open Charge Alliance publishes it and describes it as “the global open communication protocol between charging stations and charging management systems”. Version 1.6, released in 2015, is widely implemented and includes smart charging: the network can send a charger schedules that limit how much power it gives. A schedule is a list of periods, each with a limit in amps or watts, starting at an offset from the schedule’s start. A charger can hold charger-wide, default and transaction schedules at once, and must combine them into one limit; daily and weekly schedules repeat. OCPP 1.6 specification (zip) (opens in a new tab)
Schedule anchor
The moment a schedule first started. A daily schedule restarts at that time of day. The study groups its test cases by the year of the anchor.
The witness schedule has its anchor at 11:00:00 UTC on 14 September 2016. With anchors in 2017–2025 all 2,000 generated cases pass; with anchors in 2010–2016, 835 pass, 92 warn and 1,073 fail. The study traces the difference to the leap seconds since the anchor.
Signed reading
The interpretation of the standard that Harry approved in the signed spec. Where the standard’s wording allows more than one reading, the study follows this one.
The finding holds under this reading, and the study records that the standard’s wording also admits another. The signed decisions are labelled A1 to A10 in the written rules.
Vacuous pass
A passing case where the reference program gives no limit at any instant compared, so there was nothing to agree with.
The pinned report counts 55 such cases among the 2017–2025 anchors and 64 among the 2010–2016 anchors.
Tolerance
How close two limits must be to count as agreeing: within 0.05 of the profile’s unit, amps (A) or watts (W).
Correspondence review
An AI review that searched for mismatches between the model and the written rules. Its findings needed Harry’s decision and do not count as evidence.
Trusted base
The parts assumed to work correctly for a result to hold, such as the program checking the proof and the program running the tests.
