EVerest and OCPP 1.6: a formal study

AboutA study of EVerest, open-source software for electric-vehicle chargers, and how it follows OCPP.

is open-source software that runs a charging station. The Linux Foundation Energy project maintains it.

, the Open Charge Point Protocol, is the standard a charger uses to talk to the network that manages it. In version 1.6, the network can send a charger schedules that cap how much power it gives. The charger combines those schedules into one limit for each moment. The study works from OCPP 1.6 edition 2 (opens in a new tab), sections 3.13.1 to 3.13.3, 3.13.7 and 7.8 to 7.14.

The study compared EVerest’s code for combining schedules with a . It found one difference. EVerest restarts a daily schedule one second early.

That result uses the study’s of the standard, in its smallest example. The gap grows by one second for each since the schedule first started. The study rates it low severity.

Each piece of evidence has one of five strengths: Proved, Tested, Decided by Harry, Assumed or Not yet reached. Not yet reached also covers a proof that is not finished yet. The glossary says more about EVerest and OCPP, with links to their own documentation.

The study is a worked example of the argument in Review Evidence, Not Code (opens in a new tab). Harry Nicholls (opens in a new tab) directed it and built the tool it uses.

FindingA daily schedule should restart at 11:00:00; in the study’s smallest example, EVerest restarts it at 10:59:59, a leap second early.

The schedule first started at 11:00:00 UTC on 14 September 2016. At 10:59:59 UTC on 13 August 2026 the reference model gives a limit of 6,543.6 W. EVerest has already restarted the schedule and gives 9,249.9 W.

EVerest counts elapsed UTC seconds, and those include leap seconds. The reference model restarts at the clock time, as the signed reading says.

The effect on charging is small. The difference happens the same way every time.

EVerest issue #3323 reports the finding upstream. It was filed on 2026-10-29 and is open. This website does not file or update upstream issues. View filed issue (opens in a new tab)

Finding

What went wrong?

EVerest restarts a daily schedule at 10:59:59 instead of 11:00:00. That is in the study’s smallest example, under its signed reading of the standard.

For that one second, EVerest’s limit is 9,249.9 W. The reference model’s is 6,543.6 W.

The cause is leap seconds. The gap grows by one second for each leap second since the schedule first started.

EVerest issue #3323 reports this upstream. It is open. View the issue (opens in a new tab)

Does a one-second error matter?

The study rates it low severity. For one second, EVerest’s limit is too high.

The difference is small, but it happens the same way every time.

It also grows. Restarts drift one more second for each leap second since the schedule first started.

EVerest issue #3323 reports this upstream. It is open. View the issue (opens in a new tab)

One second before 11:00

The study rates this low severity. Daily and weekly restarts drift by one second per since the schedule first started.

The input has one daily default profile, no duration, and two periods: 9,249.9 W from offset 0, then 6,543.6 W from offset 40,500 seconds. Its query window begins at 03:00:00 UTC on 13 August 2026 and lasts 24 hours.

Is this a proof that EVerest is wrong?

No. The proofs are about the reference model, not EVerest’s C++ code.

The study tested EVerest by comparing it with that program on generated inputs.

The finding also depends on how the study reads the standard. The wording allows another reading, where a daily schedule repeats every 24 hours of elapsed time. That is what EVerest does.

Why it happens

. Written rules and test report · Tested, Decided by Harry

The finding depends on how you read the standard. The study writes its reading down in the signed spec, so you can check it.

Under the signed reading, a daily schedule restarts at the clock time in its startSchedule. The study notes that the wording of the OCPP 1.6 specification (opens in a new tab) allows another reading too.

EVerest works out each restart by counting elapsed UTC seconds, and those include leap seconds. The reference model uses clock time, as the signed reading says.

A diagnostic rerun shifts older forward by the leap seconds since then. All 2,000 cases then pass.

That rerun changes the inputs to confirm the cause. It does not fix EVerest.

Proof

What is proved

. Model and proofs · Proved, Not yet reached

checks mathematical arguments about the model. This is not a proof of the C++ implementation.

  • The combined limit is never above the charger-wide limit.
  • It is never above the applicable transaction limit.
  • While a transaction’s own schedule applies, changing default schedules does not change the limit.

Not yet reached: Adding a lower-priority schedule that does not apply leaves the limit unchanged (the fourth model rule, I4).

The proof check lists the completed theorems. It fails if any of them depends on sorryAx, the placeholder Lean uses for an unfinished proof, or on a non-standard axiom. The fourth, unfinished rule does not count as proved.

Tests

How was EVerest tested, and what came back?

A driver runs EVerest’s unmodified scheduling code against the reference model on 2,000 generated cases per configuration.

Schedules that first started in 2010–2016 give 835 passes, 92 warnings and 1,073 failures, as the study reported. Those failures are the finding.

Schedules that first started in 2017–2025 all pass.

A pass means the case met the study’s comparison rule, not that the limits agree exactly.

In 55 of those passing cases, the reference model gives no limit at any moment checked. There was nothing for EVerest to agree with, so those cases pass without testing anything.

Assumptions

What does the result depend on?

It depends on Lean and its standard axioms.

The reading of OCPP 1.6 that Harry approved has to be right, and the Lean model has to match it.

The compiler, the test harness and the driver, with its installation glue and two shim headers, have to work correctly.

The timezone database has to list exactly the three leap seconds since 2010.

What the result depends on

. Trusted base · Assumed

The result holds only if everything in the works correctly.

  • Lean v4.28.0 and its standard axioms (propext, Classical.choice and Quot.sound), for the completed proofs.
  • The reading of OCPP 1.6 edition 2 that Harry approved, and the Lean model matching that reading.
  • The C++ compiler, the driver with its copied installation glue and two shim headers, the Python harness, the JSON adapter and the model runner.
  • The operating system’s timezone database, which the driver reads. Its leap-second table must list exactly the three leap seconds since 2010 (2012-06-30, 2015-06-30 and 2016-12-31).

The driver compiles EVerest’s scheduling code unchanged. It adds its own installation glue and two shim headers, and the comparison trusts those too.

Limits

What wasn’t checked?

The generated inputs have limits. Each case has at most 2 charger-wide, 3 default and 2 transaction profiles, with up to 4 periods each. Offsets come in 15-minute steps, windows are 24 or 48 hours in 2026, and everything is on connector 1.

No case has default profiles on connectors 0 and 1 together.

The study has not yet reached relative profiles, phases, unit conversion, the connector-0 aggregate, offline behavior, transaction IDs or OCPP 2.x.

One of the four model rules has no finished proof.

Where the result stops

. Written rules and generator bounds · Not yet reached

Agreement on these inputs says nothing about the rest of OCPP. Each behavior not yet reached needs either a bigger model or a stated assumption.

Each case has at most 2 charger-wide, 3 default and 2 transaction profiles, with up to 4 periods per profile. Offsets come in 15-minute steps, and windows are 24 or 48 hours in 2026, all on connector 1. The generator makes absolute, daily and weekly schedules. Each case checks the moments where either program’s limit changes, and one second either side.

No case has default profiles on connectors 0 and 1 together, because the signed spec leaves open how they interact. The standard’s wording on repeating schedules also allows a second reading. Once a leap second falls between a schedule’s start and now, “every 24 hours, at the same time” can mean 24 hours of elapsed seconds or the same clock time. The study records this for the Open Charge Alliance (OCA) as note N4.

Where Harry decided

. Correspondence review · Decided by Harry

An AI searched for likely problems. Its verdict is not evidence. Harry’s recorded decisions are.

  • Harry approved two readings of the standard. A profile applies only while its schedule covers the moment (A1). A transaction profile overrules the default profiles only while its own schedule covers the moment (A2). Harry also reclassified two findings from the AI correspondence review as abstractions rather than approximations.
  • On 2026-10-27, Harry confirmed adding back a missing condition to the rule for when a schedule covers a moment (D4). The condition is s ≤ t, which says the moment t cannot come before the schedule’s start s.
  • The conformance rule (Q4) says EVerest’s limit conforms if it is at or below the model’s, or if the model gives no limit. So a lower limit counts as conforming. Harry chose to have the report warn about it anyway, because a lower limit means lost charging. The report keeps the classification caveat recorded here.

Why the study is built this way

. Study design · Decided by Harry

Each choice is listed with what it leaves unchecked.

Separate the model from the production implementation
A reference model in Lean lets the study state and prove rules about the model, then compare its answers with EVerest’s existing C++ code. A proof about the model does not show that the production code behaves the same way.
Check the moments where schedules change
The harness compares the moments where either program’s limit changes, and one second either side. That makes a one-second timing difference visible. The generator still limits profiles, periods and time windows. Agreement says nothing about other inputs.
Record interpretation decisions before judging differences
Harry settled the ambiguities in the signed spec, then reviewed the correspondence findings against those decisions. A difference that comes from a disputed reading of the standard has to stay separate from a real defect in the code.
Publish the limits beside the result
The study keeps the unfinished fourth proof, the trusted dependencies and the report’s inconsistency in plain view, with pinned inputs for replay. Shifting the inputs by the leap seconds is a diagnostic experiment. It does not fix EVerest.
