What this result covers

The EVerest study checked how a charger combines its charging schedules under 1.6. For daily and weekly schedules that started before 2017, the restart comes one to three seconds early today, and one second earlier with each future . The study rates this as low severity.

These are the limits of the claim, in the study’s own terms.

Proved Three rules about the . The combined limit is never above the charger-wide limit. It is never above the limit for the transaction. While a transaction’s own schedule applies, changing the default schedules does not change the limit.
Not yet proved A fourth rule: adding a lower-priority schedule that does not apply leaves the limit unchanged. Its proof is unfinished.
Tested EVerest’s schedule code at revision dd696165, unmodified, against the . Each test case was checked at every moment where either program might change its answer, and one second either side.
Range of the tests Up to 2 charger-wide, 3 default and 2 transaction schedules per case, with up to 4 periods each, 15-minute steps, 24- or 48-hour windows in 2026, on connector 1. Matching answers cover only these inputs.
Not tested Relative schedules, phases, conversion between amps and watts, offline behaviour, anything outside a transaction, transaction IDs, and the station-wide total on connector 0, where limits are added up across connectors. Also default schedules on connector 0 and connector 1 at the same time, where the standard is unclear.
Cause The same 2,000 older cases were run again with every schedule start moved forward by the since it. All 2,000 matched. This rerun is a diagnosis, not a fix to EVerest.
Reviewed An AI model reviewed whether the follows the written rules, and the project owner checked each finding. The AI review only points at likely problems. The owner’s decisions are the human judgment, and the owner overruled the review on two parts.
Assumed The : v4.28.0, the harness that runs EVerest’s code, and the test machine’s table, which must list the three since 2010.
Reported upstream Not yet. A draft issue for EVerest is waiting for human review. EVerest asks for every AI-assisted contribution to be reviewed by a person first.

Start with the plugin

You will need Docker, Node.js 18 or later, and Claude Code. The and checks run in Docker containers with no network access.

  1. Install the plugin from the marketplace.

    claude plugin marketplace add nicholls-inc/claude-code-marketplace
claude plugin install crosscheck@nicholls

  2. Build the checker images once, from a clone of the repository. The Lean image is slow the first time.

    git clone https://github.com/nicholls-inc/crosscheck && cd crosscheck/crosscheck
./scripts/build-docker.sh
./scripts/build-lean-docker.sh

How to use it

Install the plugin, then ask Claude in plain words. For example: “Use the agent to verify your bug fix.” You can also run each step yourself as a skill.

Prove a small piece of code with
StepWhat it does
/spec-iterateWrites the rules for the code with you, until they say what you mean.
/generate-verifiedWrites code, and checks that it follows those rules.
/extract-codeTurns the checked code into Python or Go for your project.

This suits pure, self-contained logic. Fitting the generated code into your application is still your job, and the step that turns into Python or Go is assumed correct, not proved.

Model existing code with and test it
StepWhat it does
/informal-specWrites the rules in plain English, from the standard or the intent.
/lean-specRestates those rules precisely in .
/lean-implBuilds the in and states the rules about it, ready to prove. A proof can stay unfinished, as the fourth rule’s did here.
/correspondence-reviewAn AI compares each part of the with the written rules and the code. A person decides what to do with each finding.
/drt-oracleRuns your code and the on the same generated inputs, then reports each difference it finds, with an example. This is .

A computer-checked mathematical argument that a rule always holds under stated assumptions. It does not tell us whether the rule is the right one.

A language and tool for checking that code follows written rules. It can turn checked code into Python or Go.

A language for precisely describing how code should behave, and a tool for checking mathematical arguments about those descriptions.

A program describing the behavior we expect. We compare its answers with the code being checked. It covers only the behavior it describes.

An extra second sometimes added to clock time to keep it in line with Earth’s rotation.

Run the same chosen inputs through two programs and compare their answers. A difference needs investigation. Matching answers cover only the inputs tried.

Open Charge Point Protocol: shared rules for communication between electric-vehicle charging stations and the software managing them. This study checks charging schedules under version 1.6.
