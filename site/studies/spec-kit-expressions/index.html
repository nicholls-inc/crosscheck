Spec Kit’s workflow expressions

AboutA closer look at three Spec Kit reports about the evaluator for workflow conditions.

Spec Kit workflows decide what to run with conditions such as {{ inputs.n > 10 }}. A small evaluator in Spec Kit works out each condition.

At the filing commit, the evaluator’s docstring called it “a safe Jinja2 subset”. Reports #5071, #5072 and #5073 show expressions it answered differently from Jinja2, or differently from its own other operators.

This page belongs to the Spec Kit study, which lists all 28 reports.

Download the publication record (JSON)

FindingWith n = 50, the condition 0 <= n <= 10 came out true, and the workflow took the wrong branch without an error.

The evaluator split the expression at one operator and read the rest as a single operand, so it compared 0 with a true-or-false value.

Validation accepted the condition, and the run reported success.

A grammar has since replaced the parser. The documentation now says comparisons group left to right.

Finding

What went wrong?

Some conditions gave a wrong answer instead of an error. 0 <= n <= 10 was true for n = 50. 1e3 was read as a missing variable.

Separately, == did not treat the text "10" as the number 10, while >= and <= did.

A workflow using such a condition took the wrong branch, and validation did not warn.

How do we know?

Each report has a reproduction script, and the output it gave at commit 27d14e2 on a Linux container and on macOS. Harry re-ran each one before filing.

The Jinja2 column is what Jinja2 and Python give for the same expression. Spec Kit’s own docstring named Jinja2 as the model. This website did not run either.

Upstream

What changed upstream?

A Lark grammar replaced the hand-written parser on 2 November 2026. The documentation now says comparisons share one level and group left to right.

For #5072, the maintainers made == treat numeric text as numbers, as the ordering operators already did.

A fix for #5071 is open. The fix proposed for #5073 was closed without merging.

Upstream changes

. Spec Kit pull requests
2026-10-26 and 2026-10-28
#5114 (opens in a new tab) split the evaluator into a package. #5130 (opens in a new tab) added tests that pin its existing behaviour, citing #5071 (opens in a new tab) and #5073 (opens in a new tab).
2026-11-02
#5171 (opens in a new tab) replaced the hand-written parser with a Lark grammar. The documentation now says all comparisons share one level and group left to right, so a == b > 0 means (a == b) > 0.
2026-10-23 and 2026-11-09
On #5072 (opens in a new tab) a maintainer first wrote that Python semantics, with no coercion of numeric strings, were the intended contract. #5310 (opens in a new tab) then made == and != coerce numeric strings, as the ordering operators do, and the maintainer closed the issue.
2026-11-10
#5203 (opens in a new tab), which would evaluate chained comparisons pairwise, is open. #5206 (opens in a new tab), aimed at #5073 (opens in a new tab), was closed without merging.

Main

Is it fixed on main?

Not known. Nobody has run the reproductions on main for this study.

A reading of main’s source suggests a mixed picture. Some cases now raise a syntax error, and two now evaluate correctly. 0 <= 50 <= 10 still looks true.

That reading is not evidence until a reproduction runs.

Limits

What wasn’t checked?

No reproduction ran on main, and no generated inputs were compared with Jinja2.

Spec Kit now documents some departures from Jinja2 on purpose, so Jinja2 alone is no longer a correct reference.
