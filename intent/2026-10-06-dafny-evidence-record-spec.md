# Spec: `dafny_evidence`, an evidence record from the Dafny pipeline

Intent: `intent/2026-10-06-dafny-evidence-record.md`. Governing roadmap item: ER-1. Task: ER-1.3.

This spec defines the MCP tool `dafny_evidence`. It runs `dafny verify` and `dafny audit` on a committed Dafny file and emits a version 1 evidence record (`intent/2026-10-06-evidence-record-spec.md`) with one `proved` claim, or refuses. Rules DE-1 to DE-13 state what it does. Every check exists so that the record is true of what Dafny checked: where a gap between the two was cheap to close, the tool closes it and refuses.

## Input

| Field | Type | Meaning |
|---|---|---|
| `repoPath` | string | An absolute path inside a git work tree. The tool works from the work tree's top level, `git rev-parse --show-toplevel`, called "the root" below. |
| `file` | string | The path of the `.dfy` file, relative to the root, with `/` separators. |
| `statement` | string | What is claimed, in plain language. It becomes the claim's `statement`. |
| `requirement` | string or `null` | The requirement the claim traces to, or `null`. It becomes the claim's `requirement`. |
| `theorems` | array of strings | The fully qualified names of the lemmas, methods or functions whose contracts prove the statement, as the `proved` row of the basis table in the evidence record spec asks. EV-10 checks only that each name is a non-empty string, so this tool is what holds the names to that row. The fully qualified name is the one Dafny's verification log prints: `M.C.Name` for `Name` in class `C` of module `M`, and `Name` alone for a declaration at the top level of the file. It becomes `basis.theorems`. |
| `outputPath` | string, optional | Where to write the record. A relative path is resolved against the root. DE-11 keeps it inside the work tree. |

## Output

`{ "success": boolean, "errors": string[], "record": object or null, "writtenTo": string or null }`.

`success` is `true` only when the tool built the record and, if `outputPath` was given, wrote it. `errors` is empty exactly when `success` is `true`. `record` is the record when one was built, and `null` when the tool refused before building one. `writtenTo` is the absolute path written, or `null`.

## Rules

- **DE-1. Inputs.** The tool refuses when `repoPath` is not absolute, when `file` is absolute, has a `..`, `.` or empty segment, uses `\`, or does not end in `.dfy`, when `statement` is empty after trimming white space, when `requirement` is a string that is empty after trimming, when `theorems` is empty, or when a theorem name does not match `^[A-Za-z_][A-Za-z0-9_'?]*(\.[A-Za-z_][A-Za-z0-9_'?]*)*$`. Each problem is one error.
- **DE-2. A git work tree.** The tool refuses when `git rev-parse --show-toplevel` or `git rev-parse HEAD` fails in `repoPath`. The record's `commit` is the output of `git rev-parse HEAD`.
- **DE-3. A clean tree.** The tool refuses when `git status --porcelain --untracked-files=all` fails or prints anything in the root, and names each path it printed. It also runs `git ls-files -v` and refuses, naming the path, for each entry tagged with a lowercase letter (`assume-unchanged`) or `S` (`skip-worktree`), because `git status` does not report an edit to such a file. It refuses when either command fails, which includes output past 512 MiB. That covers staged, unstaged and untracked files, and leaves out ignored ones. With DE-12, which refuses an include of an ignored or linked file, the files Dafny reads are the files at `commit`.
- **DE-4. A committed file.** The tool refuses when `git --literal-pathspecs ls-files --error-unmatch -- <file>` fails in the root, so a glob or pathspec magic in `file` names no file, and a path through a symbolic link to a directory names no file either. It also refuses when `file` is a symbolic link or not a regular file, and when `file` cannot be read, naming the error.
- **DE-5. The theorems are verified, by their fully qualified names.** DE-6 runs verify with `--log-format csv;LogFileName=/dev/stdout`, so Dafny prints one row per proof obligation after a header line that begins `TestResult.DisplayName,`. A row reads `<name> (<kind>),<outcome>,...`, with `<kind>` such as `correctness` or `well-formedness`. After DE-7 passes, the tool refuses each theorem that is not the `<name>` of a row, after the header, whose `<outcome>` is `Passed`. The name must match exactly, so `L` is refused for a lemma `L` in module `M`, and `M.L` is accepted. The log names the declarations of `file` and of every file it includes, since DE-6 passes `--verify-included-files`, and only those that carry a proof obligation, so a bodiless `{:axiom}` lemma or a lemma with no contract and an empty body is refused here too.
- **DE-6. Verify.** The tool runs `dafny verify /work/<file> --verify-included-files --log-format csv;LogFileName=/dev/stdout` in the Dafny image with the root mounted read-only at `/work` and no network. Without `--verify-included-files`, Dafny 4.11.0 checks no proof in an included file, so a theorem that calls an included `lemma Bad() ensures false {}` verifies with exit 0. The read-only mount keeps every Dafny run, including one that outlives a timeout, from writing into the tree. Every Dafny run, here and in DE-7 and DE-8, names the image by the ID that DE-8 read before the first run, not by its tag, so a tag moved during the runs does not change what runs. It refuses unless the run exits 0 and does not time out. Dafny 4.11.0 fails the run on warnings, so `assume`, a bodiless lemma with no `{:axiom}`, `{:verify false}` and an `{:extern}` with an `ensures` each refuse here.
- **DE-7. Audit.** The tool runs `dafny audit /work/<file> /work/<include>...` in the same way, naming `file` and then every file DE-12 reached, in the order reached. `dafny audit` reports only the files it is given: on 2026-10-06 an audit of a file reported 0 findings while a file it includes declared a `lemma {:axiom}`. It refuses unless the run exits 0 and its standard output and standard error together contain `Dafny auditor completed with 0 findings`. This is the check that catches `{:axiom}`, which DE-6 passes.
- **DE-8. Trusted base.** `<image>` is `DAFNY_DOCKER_IMAGE`, default `crosscheck-dafny:latest`. Before any Dafny run, the tool reads the image ID with `docker image inspect --format {{.Id}} <image>`, and refuses unless the trimmed output is non-empty. After DE-5, it runs `dafny --version` in the image and takes its trimmed standard output as `<dafny version>`. It refuses unless that matches `^\d+\.\d+\.\d+\S*$`. The trusted base is, in this order:
  1. `{"component": "Dafny verifier", "version": "<dafny version>"}`;
  2. `{"component": "Z3 solver shipped with the Dafny release", "version": "Dafny <dafny version>"}`;
  3. `{"component": "Dafny Docker image <image>", "version": "<image ID>"}`.
- **DE-9. Rerun.** `rerun.exit_code` is 0, and `rerun.command` is, with `<i>` the image, `<f>` the path `/work/<file>`, and `<fs>` that path followed by `/work/<include>` for every file DE-12 reached, each, and `<i>`, single-quoted for a POSIX shell and separated by spaces (the template below leaves `<i>` unquoted for readability):

  ```
  docker run --rm --network=none -v "$PWD":/work:ro <i> verify <f> --verify-included-files && out=$(docker run --rm --network=none -v "$PWD":/work:ro <i> audit <fs> 2>&1) && case "$out" in *'Dafny auditor completed with 0 findings'*) true ;; *) false ;; esac
  ```

  Run from the root at `commit` by a POSIX `sh`, it exits with verify's exit code when verify fails, with the audit's exit code when the audit fails, with 1 when the audit exits 0 without the clean line, and with 0 only when both exit 0 and the audit output carries the clean line. It has no pipe, because a pipe reports only its last command's exit code. The rerun differs from the tool in two ways. It carries none of the tool's memory, CPU or time limits, so it can accept a run the tool refused for those limits. It does not repeat DE-5, because the theorem names are a fact of the file at `commit` that the tool checked once. Single quoting writes `'` as `'\''`.
- **DE-10. The record.** The record is `{"format": "evidence-record/1", "commit": <DE-2>, "claims": [<claim>]}`. The claim's fields are, in order, `id`, `statement`, `requirement`, `strength`, `basis`, `trusted_base` and `rerun`. `id` is `dafny-` followed by the file path without `.dfy`, lowercased, with each run of characters other than `a` to `z` and `0` to `9` replaced by one `-`, and with leading and trailing `-` removed. When that leaves nothing, `id` is `dafny`. `statement` is the input trimmed. `requirement` is the input, trimmed when it is a string. `strength` is `"proved"`. `basis` is `{"theorems": <theorems>}` in the order given. The record satisfies EV-1 to EV-12.
- **DE-11. Output file.** When `outputPath` is given, the tool checks it before any Dafny run and refuses when: the resolved path is the root or is not inside it; a segment of it, relative to the root, is `.git`; its directory does not exist; the real path of its directory differs from the root's real path joined with that directory, so it passes through a symbolic link; it is an existing symbolic link; or it names anything that exists but is not a file whose content parses as JSON with `format` equal to `"evidence-record/1"`. The `.git` test ignores case, because a case-insensitive file system resolves `.GIT` to `.git`. So the tool overwrites an earlier evidence record and nothing else that exists: not `file`, not an include, not an existing protected surface, not an ignored file such as `.env`, not a directory and not a FIFO, whatever spelling, case or hard link names it. A path that does not exist yet passes these checks wherever it is in the tree, protected directories included, and the file written there holds only the record. After DE-13, the tool runs these checks again, because the path could change while Dafny ran, and refuses with the record on any failure. It then writes the record as JSON with two-space indentation and a final newline to a new file `<outputPath>.<pid>.tmp` in the same directory, and renames that file over `outputPath`. So a crash leaves the earlier record whole, and a link planted at `outputPath` is replaced, not followed. A write that fails makes `success` `false`, with the error, and still returns the record. Given the same inputs, commit and image, the tool writes the same bytes.
- **DE-12. Includes are tracked files.** The tool reads each `include "<path>"` in `file`, and in each file reached that way, and resolves `<path>` against the directory of the file that includes it. It refuses each include whose path is absolute, uses `\`, or resolves outside the root, and each whose resolved path fails DE-4's checks: not tracked, a symbolic link, reached through a symbolic link to a directory, or not a regular file. With DE-3, every file Dafny reads through an include is then a tracked file at `commit`, not an ignored file and not a file a link points to. The match is lexical and covers the word `include` wherever it appears, so an `include` inside a comment or a string is checked as well. An `include` that is not followed, after white space, by a plain double-quoted string is refused, naming the file, because Dafny 4.11.0 also reads `include @"x.dfy"` and `include /* c */ "x.dfy"` and the scan cannot resolve them; for the same reason a comment that merely uses the word `include` is refused. Dafny 4.11.0 also percent-decodes an include path (`L%69b.dfy` opens `Lib.dfy`, `%2e%2e` is `..`), trims trailing white space, and decodes a source file by its byte-order mark, so a UTF-16 or UTF-32 file hides its `include` lines from a UTF-8 scan. The tool therefore resolves only a path made of `A-Z a-z 0-9 _ . / -`, and refuses a scanned file, `file` included, that has a NUL byte, which UTF-16 and UTF-32 text always has. Every other include is refused, so what the tool checks is the set of plain paths in UTF-8 text, not a list of forms that were found. That can refuse a file Dafny would accept. Includes are the only files Dafny 4.11.0 reads besides `file` in this invocation: on 2026-10-06 a `dfyconfig.toml` beside the file that set `verify-included-files` did not change what `dafny verify <file>` checked, so Dafny did not load it.
- **DE-13. Nothing changed while Dafny ran.** After the Dafny runs, the tool runs `git rev-parse HEAD` and DE-3's `git status` again. It refuses when HEAD is not `commit`, naming the new HEAD, and when the status prints anything, naming each path.

## Tests

The unit tests cover DE-1, DE-5, DE-9 and DE-10 as pure functions, including a file path with a `'` and a space in DE-9, the rerun's audit of every include, and the rerun's exit code under `sh` with a stub `docker` for a passing run, a failed verify, an audit that exits non-zero with the clean line, and an audit with a finding. An integration test makes a real git repository in a temporary directory, replaces Docker with a stub, and covers DE-2 to DE-8 and DE-11 to DE-13: each refusal, and a success whose record is compared field by field with a literal. An end-to-end test, run by `npm run test:e2e` against the real image, emits a record for a proved lemma, runs its rerun command in the root and checks that it exits 0, and accepts a theorem in a class in a module only by its fully qualified name, refuses a theorem that rests on an unproved included lemma under DE-6 and on an included `{:axiom}` under DE-7, with the rerun command exiting 4 and 1 on them and 0 on a proved include, and refuses an `{:axiom}` lemma under DE-7. An MCP test calls `dafny_evidence` through the server with Docker stubbed, with `requirement` `null` and a string, and compares the returned record with a literal.

## Concerns flagged, not resolved here

- **The statement is the caller's.** The tool checks that each named theorem verifies and is declared. It does not check that the theorems' contracts say what `statement` says. Usually an LLM drafts both. Rule 1 of `docs/VISION.md` makes the statement a draft for a person to review, and the record cannot show that a person did. The property that blocks a check is a formal link between the statement and the contracts. The open question is the controlled English of rule 4.
- **DE-5 reads a log format.** DE-5 relies on the CSV columns of Dafny 4.11.0's `--log-format csv`. A Dafny release that changes them makes DE-5 refuse every theorem, which is the safe direction.
- **The rerun names a tag, not a digest.** A rerun pinned to an image digest is not yet reached. The rerun command uses the image name, so an auditor who built `crosscheck-dafny:latest` later may run a different image. The trusted base records the local image ID, which names only the image on the machine that ran the tool. The rerun does not use that ID, because an auditor on another machine builds the image and gets a different ID, so a command naming it would fail there whatever the proof. The property that blocks a digest is a published image: a digest is a registry's name for pushed content, and `crosscheck-dafny` is built locally and pushed nowhere, from a Dockerfile whose `ubuntu:22.04` base has no digest. The open question is where the image is published and how the build pins its base, which is the toolchain pinning question the evidence record spec leaves open.
- **Z3's own version is not read.** A trusted-base entry that names the Z3 build is not yet reached. The record names the Dafny release that bundles Z3, rather than Z3's own version. The property that blocks it is a deterministic way to read the version of the Z3 that Dafny runs, inside the image, with no network. The open question is whether `z3 --version` on the binary in the Dafny release, or Dafny's own report of its solver, is stable enough to record, and whether the record should name Z3 when the Dafny release already fixes it.
- **A change that is reverted during the runs is not seen.** DE-13 compares the state before and after the runs, so an edit made and undone while Dafny ran passes it. Verifying an export of `commit`, such as `git archive`, in place of the work tree is not yet reached. The property that blocks it is a mount built from the commit rather than the work tree, and the open question is whether that can be done without copying a large tree on every run.
- **The Docker runtime and the host are not in the trusted base.** On an arm64 host the amd64 image runs under emulation.
- **Any warning refuses.** DE-6 inherits Dafny's default of failing on warnings, so a missing trigger or "unusual indentation" refuses as surely as an `assume`. That is the safe direction. On 2026-10-06 it refuses all three tracked specs under `crosscheck/mcp-server/specs/`, which also hold `assume false` and one verification error (issue #81).
- **A record written into the tree dirties it.** DE-11 keeps the record inside the work tree, so DE-3 refuses the next run until the record is committed or ignored.
- **No skill calls the tool yet.** `/generate-verified` and `/spec-iterate` are Class A protected surfaces, and wiring them is a separate change, issue #80.
