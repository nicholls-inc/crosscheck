# Spec: The conformance ledger fails when `claims.json` cannot be read or parsed

Intent: `intent/2026-10-07-ledger-load-fails-closed.md`. Governing roadmap item: PB-1. Task: PB-1.23. PB-1.24 amends LL-1, LL-6 and LL-7 and adds LL-8 (`intent/2026-10-07-ledger-dangling-symlink.md`). PB-1.25 amends LL-3, LL-6 and LL-7 and adds LL-9 (`intent/2026-10-07-ledger-schema-check.md`). PB-1.40 amends LL-3, LL-6, LL-7 and LL-9 (`intent/2026-10-07-ledger-required-fields.md`).

- **LL-1. Missing file.** When reading `<root>/conformance/claims.json` fails with an error that `errors.Is(err, fs.ErrNotExist)` accepts, and LL-8 does not apply, the ledger is empty and `analyze` adds no ledger error.
- **LL-2. Unreadable file.** When the read fails with any other error, `analyze` appends one error, `[ledger] cannot read conformance/claims.json: <error>`, and the ledger is empty. A path that is a directory and a file without read permission are both in this case.
- **LL-3. Invalid content.** When the file is read but LL-9 rejects it, or `json.Unmarshal` into the ledger shape then fails, `analyze` appends one error, `[ledger] cannot parse conformance/claims.json: <error>`, and the ledger is empty. An empty file, truncated JSON, and a `narrative_claims` value that is not an array are all in this case. LL-9 runs first and reports these as faults of the schema. `json.Unmarshal` runs after it and still rejects what LL-9 does not read, such as data after the top-level object.
- **LL-4. Exit code.** An LL-2, LL-3 or LL-8 error is an ordinary error, so `report` prints `RESULT: FAIL`, which `main` maps to exit 1 as for any other error.
- **LL-5. Existing rules stand.** A ledger that decodes runs the status, `unreviewed`, `known-gap` and `present_artifact` checks as before, with the same messages.
- **LL-6. Documentation.** The header comment of `main.go` and `crosscheck/conformance/README.md` say that a missing `claims.json` is an empty ledger and that one that cannot be read or parsed, including a symlink to a missing target, or that breaks the LL-9 schema, is an error. Each names the required fields and allowed values of LL-9, says that a duplicate key fails, and says once what is not yet reached.

- **LL-8. Dangling symlink.** When the read fails as in LL-1, but `<root>/conformance/claims.json` or `<root>/conformance` is a symbolic link whose target, followed to the end, does not exist, `analyze` appends one error, `[ledger] cannot read conformance/claims.json: <path> is a symbolic link to a missing target: <error>`, and the ledger is empty. A dangling link is a ledger someone put in place and broke, so it is unreadable, not missing.
- **LL-9. Schema.** Before `json.Unmarshal` into the ledger shape, `loadLedger` checks the file against the ledger schema. It runs first because `json.Unmarshal` keeps only the last copy of a repeated key, folds case, and reads `null` into a string or a boolean as its zero value. A file that breaks it is an LL-3 error, `[ledger] cannot parse conformance/claims.json: <reason>`, and the ledger is empty.
  - **Objects.** The top level, each element of `narrative_claims` and each `check` must be a JSON object. A `null` there is `<place> is null`, and any other value is `<place> is not an object`, where `<place>` is `the ledger`, `narrative_claims[<i>]` or `narrative_claims[<i>].check`.
  - **Duplicate keys.** A key that appears twice in one of those objects is `<place> has duplicate key "<k>"`, naming the first repeat in document order. This check runs on an object before any other check reads it.
  - **Keys.** Keys match exactly, including case. A key the table below does not name is `<place> has unknown key "<k>"`, naming the first in sorted order. A required key that is absent is `<path> is missing`, naming the first in sorted order. A key that holds `null` is `<path> is null`. `<path>` is the key at the top level and `<place>.<key>` below it.
  - **Values.** A value of the wrong kind is `<path> must be <kind>`. The kinds are a string that is not blank after trimming (`a non-blank string`), any string (`a string`), `true` or `false`, and the version, which must be the JSON number written `1` (`<path> must be 1, got <raw>`).

    | Place | Key | Required | Kind |
    |---|---|---|---|
    | top level | `version` | yes | the number `1` |
    | top level | `narrative_claims` | yes | an array, as LL-3 checks |
    | top level | `description` | no | a string |
    | claim | `id`, `source`, `claim`, `reality` | yes | a non-blank string |
    | claim | `status` | yes | a string; the status allowlist checks its value |
    | claim | `check` | yes | an object |
    | claim | `tracked_in` | no | a string |
    | check | `type` | yes | `manual` or `present_artifact` |
    | `present_artifact` check | `path` | yes | a non-blank string |
    | `present_artifact` check | `expect_present` | no | `true` or `false`; absent means `true` |

  - **Check types.** A `check.type` other than `manual` and `present_artifact` is `narrative_claims[<i>].check.type is "<t>", want one of manual|present_artifact`. A `null` or non-string `type` is reported the same way, with its JSON text in place of `"<t>"`. A `manual` check takes no key but `type`. A key that the check's type does not take is `narrative_claims[<i>].check has unknown key "<k>" for type "<t>"`.
  - **Order.** Claims are checked in index order, and the first fault is the one reported. Within one object the order is: the object itself, duplicate keys, unknown keys, missing keys, then each present key in sorted order for `null` and kind. A claim's `check` is checked after the claim's own keys. In a `check`, `type` is read right after duplicate keys, because it decides which other keys are allowed.
- **Known gaps, not rules.**
  - LL-9 checks the shape of the ledger and the allowed values of `version`, `status` and `check.type`, not what the text fields say. Two claims may share an `id`, `source` need not name a real file, `tracked_in` need not name a real issue, and `check.path` may point outside the plugin root. Not yet reached: the property that blocks them is a check of each field against the tree and the tracker, and the open question is which of them can be checked without a network call. Unique claim IDs are queued as PB-1.42.
