# Intent: Each bound, choices and nullability error carries a proved counterexample

Task: CG-1.35. Governing roadmap item: CG-1. Issue: #8. Spec: `intent/2026-10-07-error-witness-spec.md` (rules WT-1 to WT-12). The split that created this row is `intent/2026-10-07-error-witness.md`.

## Problem statement
A CGV error says that a source guarantee, such as `length ≤ 64`, does not imply a target requirement, such as `length ≤ 32`. To decide whether the error is real, the reader has to work out by hand which value breaks the target. Nothing in the output names such a value, so the reader cannot run anything to check the claim.

## Proposed outcome
Each error of kind `length`, `precision`, `range`, `range_min`, `choices` or `nullability` carries a counterexample, as WT-1 to WT-12 state. The Lean checker computes it from the two constraints of the error. The checker's JSON gives it as `"counterexample"`, and `--format text` prints it as the last line of the error block. A Lean theorem with no `sorry` proves that, for every such error of `checkConstraintPair` outside the three cases of WT-1, the value is admitted by the source constraint and rejected by the target. Fixtures pin a counterexample for each kind.

The strength of the counterexample is proved, relative to the translated constraints. It is a value that the source bound admits and the target bound rejects. No library has run it. CG-1.37 runs it against Django and pydantic, and CG-1.39 asks whether the code can produce it. CG-1.40 item 1 puts that strength in the output.

## Constraints
- WT-12: no existing block of the statement manifest may change. The intent of the split assumed that a defaulted `counterexample` field on `ResultEntry` would leave the manifest unchanged. It would not: the manifest records the type of the constructor `ResultEntry.mk`, and the value hash of `buildResultEntry` and of every reporting function that `runChecker` calls. So the counterexample cannot live in `ResultEntry` or be computed inside those functions without a Tier 3 change to those blocks.
- The design that keeps the manifest unchanged: `runCheckerCx` in `Main.lean` builds the same report as `runChecker` with each entry paired with the counterexample of the diagnostic it came from. It mirrors `collectEntries`, `guardedEntries`, `stateEntries`, `Dedupe.step` and `reportStatesWith` on pairs. The theorem `runCheckerCx_fst` proves that its output is exactly `runChecker`'s, so the soundness theorems about `runChecker` still describe what the binary prints, and the exit code is unchanged. Because the binary's guarantee now runs through it, `runCheckerCx_fst` belongs among the protected theorems. TB-1.43 proposes that. Until it merges, the manifest records neither its statement nor `runCheckerCx`. A finding that deduplication merges keeps the counterexample of the entry that deduplication keeps (WT-8).
- `counterexampleOf` returns a value only after checking that the source admits it and the target rejects it (`counterexampleOf_sound`), so a counterexample in the output always has that property, whichever diagnostic it comes from. `checkConstraintPair_counterexample` gives the other direction that WT-10 asks for: every error of a WT-1 kind outside the three cases has one.
- Rule 1 of the vision: the guarantee rests on the Lean kernel, not on an LLM. The Python text is not covered by the theorem (WT-10), and `#guard` tests pin it for each kind.

## Decided by the coordinator under the maintainer's authorization
The maintainer gave the coordinating agent of this run a full-autonomy and merge grant in chat on 2026-10-21. The coordinator made the calls below under that grant. This file records the authorization; it does not constitute it, and a statement in a repository file is not maintainer sign-off.

- **Where the counterexample is computed.** A field on `ResultEntry` would change existing blocks of the manifest, so the counterexample is paired with each entry outside the protected reporting functions, and a theorem ties the paired output to `runChecker`'s (see Constraints). Adding a field to `ResultEntry` is a Tier 3 change.
- **The protection of the three theorems is a separate pull request.** The review of #133 found that the binary's guarantee runs through `runCheckerCx_fst`, and that `counterexampleOf_sound` and `checkConstraintPair_counterexample` are the guarantee of the new output field, while all three sat outside the manifest. Adding them to the theorem table, the generator and the manifest changes protected surfaces, and the governance note for that change has judgment items that only the maintainer can resolve. Rule 4 of `.claude/rules/protected-surfaces.md` makes a merge with an unresolved marker a governance violation, and the merge grant does not resolve markers. So this pull request proves the three theorems and stays Tier 2, and TB-1.43 proposes their protection in its own Tier 3 pull request (WT-12). Governing roadmap item TB-1.
- **Indentation of the text line.** WT-9 first wrote the line as `  counterexample: <text>`. Every other detail line of an error block is indented by seven spaces, so the report prints `       counterexample: <text>`, aligned with them. WT-9 now states the seven spaces. The change is cosmetic: the key text and its position as the last line are unchanged.
- **How a choices counterexample is written.** A counterexample is a Python value of the target field's type. The extractor records the value type of a choices field (`"int"` or `"str"`), and an integer choice of an `"int"` field is written as an int literal, such as `3`, not `"3"`. When the type is unknown, the string literal stays, and the spec lists that as a known gap (WT-6).
- **What "admits" means for a missing bound.** `Counterexample.admits` treats a constraint with no static bound (or no choices list) as admitting every value of its kind. That case never reaches a counterexample, because `checkConstraintPair` reports no error without both bounds.
