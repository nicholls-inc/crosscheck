# Intent: A field read through a relation or a nested data class carries the field's nullability

Task: CG-1.28. Governing roadmap item: CG-1. Issue: #6.

## Problem statement
CGV resolves a field read only one level deep. `obj.f` gets the declared contracts of field `f` when `obj` is a local of a known class. A read two or more levels deep, `order.customer.email` or `payload.address.postcode`, gets no facts at all. `attribute_facts` and `receiver_class` in `cgv/src/value_analysis.rs` resolve a receiver only through a name, and `cgv/src/model_extractor.rs` does not record what a `ForeignKey` or `OneToOneField` points at. So a `null=True` Django field or an `Optional` data class field read through a relation or a nested data class has unspecified nullability. The checker then reports a missing-guarantee warning, which CG-1.4 hides by default, instead of an error. In the real-codebase evaluation (`cgv/docs/evaluation/real-codebase-evaluation-2026-09.md`) this caused 2 of the 3 replay bugs that were reported only as warnings. The bench case `two-attribute-deep` shows it: WARNING_ONLY on `origin/main`.

Reproduced on `origin/main` 2efb07c with the two new fixtures:

```
crosscheck-contracts contracts check test_fixtures/chained_relation/ \
  --lean-checker ./prover/.lake/build/bin/contract-graph-checker --format text
RESULT: 0 errors, 0 warnings, 20 unverified. Exit code 0.

crosscheck-contracts contracts check test_fixtures/chained_dataclass/ ...
RESULT: 0 errors, 0 warnings, 9 unverified. Exit code 0.
```

Each fixture's `bad.py` holds real bugs, and each one exits 0.

## Proposed outcome
The data shape is `resolve::Link`, kept per class in `ClassInfo::links`. It records a field whose value is an instance of a project class: the qualified name of that class, and whether the field may hold None.

- Django: `model_extractor::relations` reads each `ForeignKey` and `OneToOneField` in a model body. It reads the target (first argument or `to=`) and `null=` (default `False`, `None` when it is not a literal). `extractor::relation_class` resolves the target. It accepts a class expression, `"self"`, a model name the module binds, or `"app_label.Model"` when exactly one project model `Model` lives in a module whose path contains `app_label.models`. Anything else gives no link. Links are inherited from project bases in C3 order, so a child's own definition of the name (an assignment, a method, a property or a nested class) wins, but not from a base that comes after one that is not a project model (an external mixin or a plain class), since that base may bind the same name. A `"self"` link on an abstract model is a link to each model that inherits it. An `"app_label.Model"` string is matched by package path only: `Meta.app_label` and `AppConfig.label` are not read.
- Data classes: a field whose annotation (or `Optional` of it, or a quoted name) names a project class. The annotation comes from the class that declares the field, found as `dataclasses.fields` finds it: the first base in C3 order whose fields have it, as that base resolves it. The link's nullability is the field's.

`Scope::linked_field_facts` resolves `root.l1...ln.f`. The root must be a local of a known class, the same rule as `obj.f`. Each link must be in `links`, and the function must not assign it. The result is the facts that `field_read_facts` gives for the chain's flow name `root.l1...ln.f`: the values the function assigns to it, else what `linked_declared_facts` gives: nullable when the field is declared nullable, and nothing else (see "Decided without the maintainer"). The CG-1.9 caller guards apply to the chain as they do to `obj.f`: `edge_discovery::call_guards` records a narrowed chain `a.link.f` as the parameter's field `link.f`, and `field_read_facts` keys the guard by the chain's root parameter. `flow::attr_name` now names chains of any depth, so `if order.customer.email is None: return`, `if payload.address.postcode:`, a dereference and an assignment narrow or rebind the chain as they do `obj.f`. Rebinding `obj.fk` forgets what was known about `obj.fk.*`, as rebinding `obj` already did for `obj.*`.

The spec is the `expected.json` of the fixtures below. The cases named here are the main ones, not the complete list:

- `cgv/test_fixtures/chained_relation/expected.json`. `bad.py` reads `Customer.email` (`null=True`) into the non-null `Invoice.email` through `order.customer`, and three levels deep through `shipment.order.customer` (a `OneToOneField`, then a `ForeignKey`). These two are errors, and so are the reads where the function hands an object along the chain to code that clears it (`bill_handed`, `bill_deep_handed` three levels deep), where a nested function clears it (`bill_nested`), and where the call passes the order's own customer as another argument (`bill_aliased`). It also reads a 40-character `Customer.name` into a 10-character column (`bill_short`) and a 4-place `Customer.balance` into a 2-place column (`post_balance`): each is a warning, not an error and not clean, because a chained read carries no declared length or precision. `ok.py` guards the read with `is None`, with truthiness, by guarding the nullable link, and by assigning the chain first, and gives no error. A read of the non-null `Customer.name` through a link, guarded or not, is a warning (`bill_guarded`, `bill_referrer`, `bill_referrer_unguarded`). It also has a read of `Customer.email` that its only caller guards (`bill_caller_guarded`), which must be a warning and not an error, and the cases that keep that caller guard or end it by a rebind, an identity test or a nested function that only reads (`bill_after_rebind`, `bill_checked`, `bill_formatted`), each a warning.
- `cgv/test_fixtures/chained_dataclass/expected.json`. The same cases through a nested `@dataclass` and a nested pydantic model, with three errors (the third is a method that calls `super().reset()` before the read) and the required warnings for the guarded reads of a non-null field. `unchecked.py` reads a length and a precision through a data class link, and each is a required warning.
- `cgv/test_fixtures/chained_unreached/expected.json`. A chain through a reverse relation, a target named by `settings.AUTH_USER_MODEL`, an `"auth.User"` target that names no project model, and a chain whose root is a call result each read as unknown: a warning, no error and no silence.
- `cgv/test_fixtures/chained_write/expected.json`. `clear_name` writes None to the non-null `Customer.name` through `order.customer.name`, which edge discovery does not record. `copy_name` copies `order.customer.name` into the non-null `Invoice.name`. The run must report that read as a warning. It exits 0, because a warning does not change the exit code, and an error needs the write to be checked (CG-1.52).

`extractor::tests::test_links` pins the resolution rules: inheritance, `to=`, `"self"`, a non-literal `null=`, `"app.Model"`, an unresolvable `"auth.User"`, a non-project target, a quoted `Optional["Address"]`, a `list[Address]` that is no link, and an inherited data class field. `test_links_follow_python_lookup_order` pins the data class order (`C(A, B)` and the diamond `D(A2, B2)`) and a link hidden by an external or plain base. `flow::tests::test_attribute_chains_narrow_and_rebinding_a_link_forgets_them` pins chain narrowing and forgetting, and it fails if the old early return in `forget_attributes` comes back. `value_analysis::tests::test_linked_field_facts` pins each branch of `linked_field_facts`, the rule that only a declared nullable carries through a link, the caller-guard lowering of a chain, a nested function or lambda whose parameter shadows the caller's name, defaults, and stores by `for`, `with` and comprehension targets.

## Affected users and systems
- People who run `crosscheck-contracts contracts check` on a project that reads model or data class fields through relations or nested data classes. A field declared nullable read through a link into a non-null target becomes an error. Every other declared guarantee of a field read through a link stays unverified, as before, so its bugs are warnings. On the bench, `two-attribute-deep` moves from WARNING_ONLY to CAUGHT, and `bench/baseline.json` and the README table record it. No other case changes. All 109 fixtures pass. The labelled run keeps precision 0.67 on 3 errors.
- `cgv/src/resolve.rs` (`Link`, `ClassInfo::links`, and `ProjectIndex::annotation_class`, moved from `value_analysis.rs` so the extractor can use it), `cgv/src/model_extractor.rs` (`relations`), `cgv/src/extractor.rs` (links for Django models and data classes), `cgv/src/flow.rs` (`attr_name`, `forget_attributes`), `cgv/src/value_analysis.rs` (`linked_field_facts`, `linked_declared_facts`, `field_read_facts`), `cgv/src/edge_discovery.rs` (`call_guards`), and `cgv/README.md`. No Lean file changes, so `protected-statements.txt` stays the same.

## Constraints
- The tier is 2: a behavioural change to the extractor, with no protected path.
- A one-level read `obj.f` relies on every write to the field being checked against its contracts. A chained read cannot rely on that: a write through a chain (`order.customer.name = None`) or through an alias (`c = order.customer; c.name = None`) is not an edge, so a None, or a value longer or more precise than declared, can be stored in the field. The review of #132 ran both and got exit 0 with no warning. So a chained read carries no declared guarantee but a nullable one, and CG-1.52 records the write rule that would let it carry the rest.
- Effect on the guarantee: exit 0 promises the same for every input, except reads through a link. There, a read that used to be unverified is nullable when the field is declared nullable, and otherwise stays unverified. No declared fact is trusted through a link, because a write through a chain or an alias is not checked against the field (CG-1.52).
- Not yet reached: a reverse relation (`customer.order_set`, the reverse side of a `OneToOneField`), a target named by `settings.AUTH_USER_MODEL`, a model name defined in another module that the declaring module does not import, an `"app_label.Model"` string that does not name exactly one project model in an `app_label.models` module, a chain whose root is not a local of a known class (`get_order().customer.email`), and a chain whose link the function assigns. Each still reads as unknown, so each is unverified as before and is never silent. The blocking property is that a link is resolved only from the field's own declaration. The open question is whether a project-wide model registry is worth building for the rest.
- Edge discovery still records a write only through `obj.f`, so `order.customer.email = None` is not a write to `Customer.email`. That is the existing write rule, and this task does not change it (CG-1.52).
- The review of #132 left LOW findings that this task does not fix, listed in CG-1.53.

## Decided without the maintainer
The maintainer was away. The coordinating agent made each decision below under the maintainer's full-autonomy and merge grant, which the maintainer gave to it in chat on 2026-10-21. This file records that authorization. It does not constitute it, and a reader can confirm it only with the maintainer. The task row left one question to the intent: whether a read through a relation that may be None is a finding. The review of #132 raised the others.

A link that may be None (`ForeignKey(null=True)`, an `Optional` nested class, or a `null=` that is not a literal) raises `AttributeError` when it is None. It does not yield None, so no None reaches the target through it. Reporting a nullability error there would be a false error, because the value the write receives is never None from that cause. CGV has no constraint for "dereferences None" (see the README's `none-dereference` case, which is not yet reached).

Decision 1 (review of #132): a chained read (two or more levels) carries no declared guarantee of the last field. Its declared length, precision, range, choices, type and non-null are all unknown, so a target that requires one of them gives a warning ("no ... guarantee"), not an error and not silence. A field declared nullable still reads as nullable, which can only make the read more pessimistic, so a real nullability bug is still an error. The reason is the unchecked write: `a.b.f = v` or `x = a.b; x.f = v` elsewhere can store a value that breaks any declaration of `f`, and trusting the declaration made such a read exit 0 with no warning (`chained_write`). Once the function narrows the chain (`if order.customer.name is None: return`) or stores a value into it, the read has the facts of what the guard or the store shows. This decision also covers the earlier question: a non-null field read through a nullable link is a warning, for the same reason as through any link. The rule that lowered a non-null read through an unnarrowed nullable link is gone, since no input can reach it any more, and `Link::nullable` is read by nothing until CG-1.52 lets a chained read regain the declared guarantees. Earlier rounds kept length, precision, range, choices and type. The fourth round of review showed that the same unchecked write breaks them, so they are dropped too.

Decision 2 (review of #132): the CG-1.9 caller-guard lowering applies to chained reads. A chained read of a nullable field that every caller narrows has unknown nullability, so it is a warning, as the one-level rule gives, and not an error (`bill_caller_guarded`).

Decision 3 (review of #132): a data class takes an inherited field's annotation in the order Python does, the C3 order the links use, through each base's own inherited fields (`dataclasses.fields` takes each base's fields whole, the first base last). It took the last base's before. Fields themselves (`with_inherited`, `fields_with_inheritance`) still let a later base win, and unifying the three walks is CG-1.53.

Decision 4 (review of #132): a model does not inherit a link from a project model that comes after a base that is not a project model in its C3 order. That base may bind the same name, and CGV cannot see what it binds, so the read gets no link facts and stays unverified.

Decision 5 (round 4 of the review): the hand-off walk in `cgv/src/flow.rs` is scope-aware. A name a nested function or lambda takes as its own parameter is not the caller's for reads as well as writes, and defaults run in the caller's scope. A store to a chain that the walk does not track as an assignment (a `for`, `with` or comprehension target, or a store in a default) ends the caller's guard on chains of the same root. A name a nested function binds locally is still counted as the caller's, which gives a false error rather than a missed one, and the README says so.

The maintainer could choose instead to check writes through chains and aliases first (CG-1.52) and then let a chained read carry the field's declarations. Or the maintainer could report an unguarded nullable link as an error of its own kind (a None dereference), which needs a new constraint kind in the checker and is Tier 3.

## Unconfirmed by the maintainer (review pass 3)

It does not rely on the grant above, so the maintainer should confirm each item: (a) the hand-off walk records an object along a chain read as a value at any depth, so `helper(p.a.b)` ends the guard on `p.a.b.f`; any attribute read as a value still ends the guards on every chain of its root, which gives false errors on a plain field read and is stated in the README; (b) a `super()` call, however it is used, ends every guard, since the walk does not know which parameter is the method's own object; (c) a call that passes a parameter together with another argument that is the same object, an object along its guarded chain or an expression built from the parameter (also one that `*args` takes) ends that chain's guard, and the same alias for a plain field is left as it was; (d) a `"self"` link on an abstract model is inherited as a link to the nearest model in C3 order that lists the abstract model among its bases, directly or through abstract models only (a multi-table child of that model links to the model); (e) a method, property, nested class or chained assignment in a model body hides an inherited link; (f) the string-target matching by package path is documented, not changed. A bound method or a property of an object along a chain, read as a value, an alias made in the caller and a reference to the frame are not yet reached; the README names the blocking property.
