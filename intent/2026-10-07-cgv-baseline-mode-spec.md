# Spec: Baseline mode reports only the findings that a change introduces

Intent: `intent/2026-10-07-cgv-baseline-mode.md`. Governing roadmap item: CG-1. Task: CG-1.5.

The rules apply to `contracts check`. A *result* is one entry of the `results` array of the checker's JSON. Its *class* is incomplete, error, warning or unverified, as UC-1 in `intent/2026-10-07-cgv-unverified-coverage-spec.md` defines.

- **BL-1. Flags.** `--write-baseline PATH` and `--baseline PATH` are options of `contracts check`, in both formats. They may be given together. `--baseline` and `--evidence-record` cannot be given together, and the argument parser rejects the pair.
- **BL-2. Root.** The *root* of a run is its application path when that path is a directory, and the path's parent directory when it is a file.
- **BL-3. Key.** Every result that is not incomplete has a key with these fields: `class` (`error`, `warning` or `unverified`), `source` (the source node's `name`), `target` (the target node's `name`), `hop`, `source_guarantee`, `target_requirement`, `site_file` and `site_text`. `site_file` is the result's `site.file`, or the empty string when the result has no site. `site_text` is null when `site_file` is empty. Otherwise it is line `site.line` (counted from 1) of the file `site_file` under the root, decoded as UTF-8 with invalid bytes replaced, with leading and trailing whitespace removed and every run of whitespace replaced by one space. The key holds no line number. When the file cannot be read or has fewer than `site.line` lines, the run prints an error naming the file and exits 2.
- **BL-4. Baseline file.** A baseline file is a JSON object `{"format": "cgv-baseline/1", "findings": [...]}`, where each finding is a key as a JSON object with the field names of BL-3. The findings are sorted, so two runs with the same results write the same file.
- **BL-5. Write.** With `--write-baseline PATH`, the run first removes any file at PATH. If the checker prints a JSON result that has no incomplete result and an exit code of 0 or 1, the run writes a baseline file with the key of every result to PATH. Otherwise it writes no file. Writing changes neither the output nor the exit code, which follow the other rules (BL-8 to BL-10 when `--baseline` is given, the checker's otherwise).
- **BL-6. Read.** With `--baseline PATH`, the run reads PATH before extraction. A file that is missing, unreadable, not JSON, has a `format` other than `cgv-baseline/1`, or has a finding without one of the fields of BL-3, makes the run print an error and exit 2 before the checker runs.
- **BL-7. Match.** For each key, let `b` be the number of baseline findings with that key and `c` the number of results of the run with that key. When `c <= b`, each of the `c` results is *existing*. When `c > b`, each of the `c` results is *new*. The key has `max(0, b - c)` *fixed* findings, and the fixed findings of a run are those keys, each repeated that many times, in the order of BL-4.
- **BL-8. Exit code.** With `--baseline`, let `x` be the checker's exit code. When `x` is not 0 or 1, or some result is incomplete, the run exits `x`, or 2 when `x` is 0 or 1. Otherwise it exits 1 when some error is new, or when `x` is 1 and the run has no error. Otherwise it exits 0. So a run whose checker reports an error that no baseline finding matches exits 1.
- **BL-9. JSON output.** With `--baseline`, the run prints the checker's JSON object with three changes. `results` keeps only the new and incomplete results, in their order. `exit_code` is the exit code of BL-8. A key `baseline` is added, holding `checker_exit_code` (the checker's `exit_code`), `new` and `existing` (each an object with the number of `errors`, `warnings` and `unverified` results of that status), and `fixed` (the fixed findings of BL-7, as keys). Every other field is kept. Without `--baseline`, the JSON is the checker's output byte for byte.
- **BL-10. Text output.** With `--baseline`, the body prints only incomplete and new results, by the rules UC-2 to UC-5. The coverage section counts every unverified result of the run, new or existing. Before the `RESULT:` line, the report prints `BASELINE: <a> error(s), <b> warning(s), <c> unverified in the baseline, not shown.`, where `a`, `b` and `c` count the existing results. When the run has fixed findings it then prints `FIXED: <n> finding(s) in the baseline not reported by this run:` and one line per fixed finding, `  <class> <hop source> → <hop target> at <site_file>: <site_text>`, with ` at ...` left out when `site_text` is null. The last line reads `RESULT: <a> new error(s), <b> new warning(s), <c> new unverified. Exit code <x>.`, where `x` is the exit code of BL-8.
- **BL-11. Nothing dropped.** In both formats, the number of results printed or kept, plus the existing counts, equals the number of results of the checker.

**Known gaps, not rules.**
- **A finding swapped for an equal one is not yet reached.** A change that removes one finding and adds another with the same key (same source, target, hop, bounds, site file and site line text) leaves the count unchanged, so BL-7 reports neither. The blocking property is that the key holds no position, by design, so an edit above a finding does not make it new. The open question is whether a finer field, such as the text of the enclosing function, can tell such a pair apart without making unrelated edits churn the key.
- The baseline is input that the user trusts. A baseline made from another commit, other options or another CGV version can only fail to match, which makes findings new, or match a finding with an equal key. Exit 0 in baseline mode says that every error the checker reported had a baseline finding with an equal key. It does not carry the guarantee of `runChecker_sound_all`, which is why BL-1 refuses `--evidence-record`.
- The class is the report's class (UC-1), read from the checker's wording. CG-1.31 moves it into the checker's JSON.
